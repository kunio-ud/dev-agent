# UT観点カタログ

## 優先度

- Must: リリース前に必ず確認する観点。正常系、主要エラー、権限、validation、業務仕様で定義された例外ハンドリングを含める。
- Should: 品質向上のために確認する観点。境界値、副次的エラー、retry詳細、ログ/監査など、仕様とリスクに応じて追加する。

## Service

Service は基本設計の処理・業務判断を持つため、UTの主対象にする。

| 観点 | 確認内容 |
|---|---|
| 正常系 | 期待する戻り値、Repository呼び出し、状態変化 |
| 入力検証 | 必須、型、桁数、形式、範囲、制御文字、長大入力、型強制変換、バリデーション通過後も業務ロジック内で注入的な値が意図せず使われないこと |
| 業務分岐 | 条件ごとの戻り値、処理スキップ、エラー |
| 権限 | 権限あり/なし、ロール差分 |
| 状態遷移 | 許可される遷移、禁止される遷移 |
| 重複/競合 | 既存データあり、重複登録、競合更新 |
| 並行処理 | 冪等性、同時実行時の重複防止、二重送信防止。楽観ロックそのものは結合テストへ回す |
| Repository結果 | found/not found、空配列、複数件、例外 |
| 外部IF結果 | 成功、失敗、timeout、retry対象 |
| Result/Either | ok/error の両方、error code、message |
| 副作用 | Repository save、通知、イベント発行。監査ログは「ログ/監査」観点で扱う |

## 純粋関数

| 観点 | 確認内容 |
|---|---|
| 境界値 | 0、1、最大、最小、空文字、null相当 |
| 変換 | 入力から出力への mapping |
| 並び順 | sort、filter、grouping |
| 日付 | 月末、年跨ぎ、timezone、営業日 |
| 丸め | 小数、金額、割合、単位変換 |
| 不変性 | 入力オブジェクトを破壊しない |

## Repository

RepositoryはService UTではmock/stub/fakeの候補にする。ただし、DB制約、ORM mapping、transaction、外部キー制約が品質リスクの場合は、DB込みテストまたは結合テストで扱う。

| 観点 | 扱い |
|---|---|
| query条件構築 | 単体または結合 |
| DB制約 | 結合 |
| transaction | 結合 |
| mapping | 単体または結合 |
| not found | Service UTではmock/stub/fakeの戻り値で確認 |

## 時刻/UUID/random

- `now()`、UUID、乱数は直接呼ばず、依存として渡せるなら渡す。
- 固定値を返すstubでテストする。
- タイムゾーンや日付境界は観点として明示する。

## ログ/監査

- 業務上必要な監査ログはUT観点に含める。
- 単なるdebugログはUTで過度に固定しない。
