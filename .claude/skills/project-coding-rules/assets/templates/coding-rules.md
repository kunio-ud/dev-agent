## 2. 基本方針

- 既存コードの構成・命名・責務分割を優先する。
- 無関係なリファクタや整形で差分を広げない。
- 新規依存追加は理由を明記し、必要に応じて事前確認する。
- セキュリティ、DB破壊、外部IF変更は事前確認する。
- サーバーサイドはリポジトリパターンを採用する。
- Service に基本設計書の処理・業務ロジックを置く。
- 言語に関わらず、関数型プログラミング寄りに実装する。

## 4. アーキテクチャ方針

### 4.1 サーバーサイド

| 層 | 責務 | 配置 |
|---|---|---|
| Controller / Handler / Route | 入出力境界。業務判断を書かない |  |
| Service | 基本設計の処理・業務ロジック |  |
| Repository | DB/永続化/検索。業務判断を書かない |  |
| DTO / Schema / Mapper | 入出力変換・検証 |  |

### 4.2 関数型プログラミング

- 純粋関数、明示的な引数と戻り値、immutable なデータを優先する。
- 副作用は Repository、外部IF、IO境界に寄せる。
- 共有 mutable state、singleton、継承中心の設計を避ける。

### 4.3 TypeScript / JavaScript

- `class` を禁止する。
- `this` を禁止する。
- Service/Repository は関数または plain object の関数プロパティとして定義する。
- 依存は factory 関数または引数で注入する。
- フレームワークや外部APIが class を強制する場合は、例外理由を明記する。

## 10. 実装前チェック

## 11. レビュー観点

- [ ] 既存構成・命名に合っている。
- [ ] 仕様外の挙動を追加していない。
- [ ] サーバーサイドで Service / Repository の責務が分離されている。
- [ ] Service に基本設計の処理が実装されている。
- [ ] 関数型方針に反していない。
- [ ] TypeScript/JavaScript で `class` / `this` を使っていない。
- [ ] エラー・境界条件を扱っている。
- [ ] テストが追加/更新されている。
- [ ] ログ・監査・権限の扱いが妥当。
