# テスト方針

## 基本方針

- 既存テストの粒度、命名、配置、ヘルパーを優先する。
- 新規テストは、正常系だけでなく主要な異常系と境界値を含める。
- バグ修正では、再発防止テストを先に追加できるなら追加する。
- テストできない場合は、理由と代替確認を明記する。

## 変更タイプ別

| 変更タイプ | 推奨テスト |
|---|---|
| UI | 表示、入力、バリデーション、権限別表示、主要操作 |
| API | 正常系、バリデーションエラー、認証認可、NotFound/Conflict |
| DB | マイグレーション、既存データ、制約、インデックス影響 |
| バッチ | 正常終了、0件、部分失敗、再実行、リカバリ |
| 外部IF | 送受信、タイムアウト、リトライ、フォーマット不正 |
| セキュリティ | 権限不足、入力攻撃、秘密情報露出、監査ログ |

## 検証コマンドの選び方

- まず最小の対象テストを実行する。
- 共有部品を触った場合は関連範囲を広げる。
- リリース影響が大きい場合は全体テストまたはビルドも実行する。
- フロントエンド変更では可能なら画面確認、スクリーンショット、アクセシビリティの基本確認を行う。
