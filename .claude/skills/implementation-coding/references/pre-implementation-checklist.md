# 実装前チェックリスト

## 入力確認

- 要件ID、基本設計ID、チケット番号が分かるか。
- 先行して作成されたUT観点/UTケースがあるか。
- 期待する振る舞いと受入条件が分かるか。
- 変更対象が UI/API/DB/バッチ/外部IF/設定 のどれか分かるか。
- 互換性、移行、権限、監査、性能の影響があるか。

## コード調査

- 関連する既存実装を検索したか。
- 先行UT観点/UTケースがある場合、実装で満たすべき振る舞いとして確認したか。
- 同種機能の実装パターンを確認したか。
- テスト配置と命名規則を確認したか。
- 設定、環境変数、ルーティング、DI、権限定義を確認したか。
- DB変更の場合、マイグレーションと既存データ影響を確認したか。

## unit-test-design 呼び出し判定

- 新機能追加、複雑な業務分岐、権限制御、状態遷移、外部IF呼び出しを含む変更か。
- 該当する場合は、テストコードを書く前に `unit-test-design` でUT観点/UTケースを整理する。
- 既存テストへの小さな追加だけで済む場合は、既存スタイルに合わせて直接追加してよい。

## ブロッカーとして確認するもの

- データ削除、破壊的マイグレーション、既存APIレスポンスの互換性破壊。
- 認証認可、個人情報、秘密情報、監査ログに関わる仕様不明点。
- 外部システム連携の契約変更、接続先変更、エラー時責任分界。
- 受入条件がなく、成功判定ができない変更。

## TODO化して進められるもの

- 文言、表示順、軽微なスタイルなど後で調整可能なもの。
- 性能目標の厳密値が未確定だが、既存水準で実装できるもの。
- ログ文言や運用メッセージなど、後続レビューで確定できるもの。
