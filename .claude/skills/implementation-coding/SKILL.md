# 実装コーディングスキル

## 目的

要件定義書・基本設計書・既存コードを入力として、既存システムに沿った実装変更を行う。
本スキルは「コードを書く」だけでなく、影響範囲の確認、実装方針、テスト、レビュー、残リスクの説明までを扱う。

## このスキルの位置づけ

推奨工程:

`requirements-definition-doc` → `basic-design-doc` → `unit-test-design（設計先行）` → `project-coding-rules` → `implementation-coding` → `unit-test-design（差分確認）` → `test-design`

ただし、設計書がない小さな改修でも使える。その場合は、ユーザー依頼と既存コードを根拠に最小限の実装メモを作ってから進める。

## 先に読む参照

必要に応じて以下を読む。

- 実装前チェックリスト: [references/pre-implementation-checklist.md](./references/pre-implementation-checklist.md)
- 実装レビュー観点: [references/review-checklist.md](./references/review-checklist.md)
- テスト方針: [references/testing-guidelines.md](./references/testing-guidelines.md)

## 入力として確認する情報

不足していても作業を止めない。ただし、破壊的変更、外部仕様変更、データ破壊リスク、セキュリティ影響がある場合は確認する。

- 対象機能、要件ID、基本設計ID
- **`docs/development/CODING_RULES.md`**（最優先）— `project-coding-rules` の成果物。命名規則・ディレクトリ構成・エラー実装形・ログフォーマット・Lint・テストツールの正
- **基本設計書「2.4 アーキテクチャ方針・実装制約」** — `CODING_RULES.md` の根拠（採用ライブラリ、レイヤー責務、横断ライブラリの選定）。`CODING_RULES.md` が無い場合はこちらを直接参照
- **基本設計書の API 物理定義（`openapi.yaml`）** — API を実装/変更する場合の SSoT
- **基本設計書の TODO 集約レポートに残っている `BLOCKER` 項目** — 未解決なら実装を進めず確認する
- 先行して作成されたUT観点/UTケース
- 期待する振る舞い、受入条件
- 変更対象の画面/API/DB/バッチ/外部IF
- 既存の実装パターン、テストパターン、命名規則
- 互換性、移行、リリース制約

## 実装手順

1. **コードベースと設計書を読む（読み順は厳守）**
   - **第一優先: `docs/development/CODING_RULES.md`** — `project-coding-rules` の成果物。命名・配置・エラー実装形・ログフォーマット・Lint・テストツール等、実装の具体形はここを正とする。
   - **第二優先: 基本設計書「2.4 アーキテクチャ方針・実装制約」** — `CODING_RULES.md` の方針根拠（採用ライブラリ・レイヤー責務・横断ライブラリの選定）。`CODING_RULES.md` が無い／曖昧な場合はここを直接参照する。
   - **両者が食い違う場合**: 2.4 を優先し、`CODING_RULES.md` の修正をユーザーに提案する（独断で判断しない）。
   - **どちらも無い場合**: 既存コードから規約を読み取り、`project-coding-rules` の起動を提案する。
   - API を扱う場合、`openapi.yaml`（基本設計の SSoT）から `operationId`・`x-api-id`・IO スキーマを読む。Markdown 側に API 一覧があっても、物理定義の正は YAML。
   - 関連ファイル、既存パターン、テスト、設定、ルーティング、データモデルを確認する。
   - 先行して作成されたUT観点/UTケースがある場合は、実装で満たすべき振る舞いとして確認する。
   - 新しい抽象化や依存追加は、既存パターン・`CODING_RULES.md`・2.4 で解けない場合だけ検討する。

2. **変更範囲を決める**
   - UI、API、DB、サービス層、バッチ、テスト、設定のどこを触るか明示する。
   - 触らない範囲も決め、無関係なリファクタを避ける。

3. **実装方針を短く固める**
   - 既存設計に合わせる。`CODING_RULES.md`（具体形）と基本設計 2.4（方針根拠）を**そのまま採用する**。「今の流行りはこっち」「ベストプラクティス的にはこう」という理由での独断置換は禁止。
   - **`CODING_RULES.md` と 2.4 で食い違いがある場合**: 2.4 を優先し、`CODING_RULES.md` の修正をユーザーに提案してから実装する。
   - **設計から逸脱せざるを得ないと判断した場合は、実装を進めず停止してユーザーに報告する**（例: 指定ライブラリが対象機能で破綻する、既存コードと矛盾する、等）。設計書を改訂してから実装する。
   - プロジェクト規約がない場合の既定方針として、サーバーはリポジトリパターン、Serviceに基本設計の処理、言語に関わらず関数型プログラミングを採用する。
   - TypeScript/JavaScript では `class` と `this` を使わない。ただし外部フレームワークが強制する場合は例外理由を明記する。
   - 入出力、状態変化、エラー、権限、監査、性能への影響を確認する。
   - DBスキーマや外部IFを変える場合は後方互換性と移行を確認する。
   - **API 実装時の型生成**: プロジェクトに `openapi-typescript` / `openapi-generator` 等のコード生成ツールが導入されている場合は、`openapi.yaml` から型・クライアント・サーバースタブを生成して使う（手書きは Drift の温床）。導入されていない場合は無理に導入せず、`openapi.yaml` を正として手書き型を合わせる。

4. **実装する**
   - 小さく変更し、既存の命名、配置、エラーハンドリング、ログ、型、バリデーションに合わせる。
   - 仕様外の見た目変更、依存追加、広範囲リファクタは避ける。

5. **テストする**
   - 変更に対応する単体/結合/画面/API/バッチテストを追加または更新する。
   - 既存テストがある場合は同じ粒度・同じスタイルで追加する。
   - 新機能追加、複雑な業務分岐、権限制御、状態遷移、外部IF呼び出しを含む変更では、`unit-test-design` でUT観点/UTケースを整理してからテストコードを書く。
   - 既存テストへの小さな追加だけで済む場合は、既存スタイルに合わせて直接追加してよい。
   - **既存テストが落ちた場合は、デグレードの兆候として扱う**。実装を直すのが第一手であり、**テストの期待値書き換え・コメントアウト・skip による「緑化」は禁止**。既存テスト自体が間違っていると判断した場合のみ、理由（仕様変更・元々のテストバグ等）を明記してユーザーに修正可否を確認する。

6. **確認結果をまとめる**
   - 変更内容、検証コマンド、残リスク、未確認事項を簡潔に報告する。
   - テスト未実行の場合は理由を明記する。

## 変更タイプ別の重点

| 変更タイプ | 重点確認 |
|---|---|
| UI | 状態管理、入力検証、アクセシビリティ、レスポンシブ、既存デザイン |
| API | リクエスト/レスポンス、認証認可、エラー、互換性、OpenAPI/型 |
| DB | マイグレーション、既存データ、ロールバック、インデックス、性能 |
| バッチ | 入出力、冪等性、再実行、リトライ、監査ログ、締め時間 |
| 外部IF | 接続先、タイムアウト、リトライ、異常時、契約変更 |
| セキュリティ | 認証、認可、入力検証、秘密情報、監査ログ、権限昇格 |

## 実装判断の原則

- 既存コードの流儀を優先する。
- サーバーサイドは Controller/Handler、Service、Repository の責務を分ける。
- 業務ロジックは Service に置き、Repository に業務判断を書かない。
- 関数型方針を優先し、共有 mutable state と継承中心の設計を避ける。
- 要件・設計・既存テストのどれにもない振る舞いを勝手に足さない。
- 共有部品を変える場合は呼び出し元を確認する。
- 失敗時の動作を成功時と同じくらい明確にする。
- 仕様が曖昧な場合は、仮置きではなく確認すべきものと、TODOで進められるものを分ける。

## やってはいけないこと

- 無関係なリファクタや整形で差分を広げる。
- 既存のユーザー変更を巻き戻す。
- 理由なく新しい依存、フレームワーク、設計パターンを導入する。
- **`CODING_RULES.md` や基本設計 2.4 に明記されたライブラリ・レイヤー責務を、独断で別物に置き換える。** 変更が必要なら、まず `CODING_RULES.md` ／ 2.4 のどちらを改訂すべきか整理してから実装する。
- **基本設計書の TODO 集約レポートに `BLOCKER` が残っている状態で実装を進める。**
- **既存テストを「通す」ために期待値を書き換える、コメントアウトする、skip する。** 落ちたテストはデグレードの兆候。テスト自体の修正が必要な場合は理由を明記してユーザーに相談する。
- テストを壊したまま、または未確認のまま成功扱いにする。
- セキュリティ、DB破壊、外部仕様変更を暗黙に進める。

## 完了報告

完了時は以下を短く報告する。

- 変更した内容
- 変更した主なファイル
- 実行した検証
- `docs/evidence/implementation.evidence.json`（実装完了の証拠、検証コマンド、BLOCKER 0件の証明、成果物 hash）
- 未実行の検証と理由
- 残リスクまたは次に確認すべき事項
