# 要件定義書作成スキル

## 目的

日本のSI案件で使いやすい**要件定義書**を作成・更新する。
要件定義は「何を達成するか」「どこまでを対象にするか」「満たすべき条件は何か」を合意する工程であり、基本設計に渡せる粒度でまとめる。

本スキルでは、実装方式や画面・DB・APIの詳細設計には踏み込まない。基本設計スキルへ渡す前段として、要件ID、優先度、受入条件、トレーサビリティを明確にする。

## このスキルのBase

このスキルは、公式・準公式の要件定義/要件工学の考え方と、現場で使う基本設計への引き継ぎ様式の両方をBaseにする。

優先順位:

1. **顧客指定テンプレート/社内標準/過去案件様式**: 指定がある場合は最優先。
2. **公的・準公的Base**: ISO/IEC/IEEE 29148:2018、IPA 共通フレーム2013、IPA 非機能要求グレード2018。
3. **実務Base**: 既存スキル [basic-design-doc](../basic-design-doc/SKILL.md) へ渡せるよう、要件IDから画面、帳票、データ、外部IF、API、DB、処理フロー、テスト観点へ追跡できる形にする。

Baseの詳細は [references/standards-basis.md](./references/standards-basis.md) を読む。

## 入力として集める情報

不足していても作業を止めず、TODO に逃がす。**ただし TODO は 2 種類を厳密に使い分ける**（後続の `basic-design-doc` と同じ運用）。

| 記法 | 用途 | 即時アラートの要否 |
|------|------|---------------|
| `【TODO(BLOCKER): 〇〇を確認】` | これが未解決だと**要件FIX前に必須**。後続の基本設計フェーズ着手不可レベル（システム化範囲・主要業務フロー・認証方式・適用法令・連携先 等） | **ユーザーへ即時アラート**（章の完成を待たない） |
| `【TODO: 〇〇を確認】` | 基本設計／詳細設計／運用フェーズで決めても進められる項目 | TODO 集約レポートへ |

**ブロッカー項目を見つけたら、その章の執筆完了を待たず、即座にユーザーに対して質問・アラートを出す。** 要件定義書を書き終えてから「実は不明でした」を出すと、基本設計が止まる。

**必須インプット**
- 対象システム名、目的、背景、解決したい課題
- 主要ステークホルダー（利用者・管理者・外部システム・運用担当）
- 現行業務・現行システムの概要と課題

**あれば望ましいインプット**
- RFP、提案書、ヒアリング議事録
- 現行システムの機能一覧・画面・帳票・データ仕様
- 既存のID命名規則
- 非機能要求に関する数値（SLA、性能目標、ユーザー数）
- セキュリティ・コンプライアンス制約

**着手前にユーザーに確認すべき項目**

**判断基準: 質問するか TODO にするか**

| 判断 | 条件 | 例 |
|---|---|---|
| **質問する** | 作業の方向性が決まらない・章構成が確定しない | 作成スコープ、シナリオ種別 |
| **質問する** | 顧客合意が必要で仮置きが危険なもの | セキュリティ制約、法令要件 |
| **TODO化** | 後続フェーズで確定すれば支障ない | 非機能の具体的数値、ID命名の詳細 |
| **TODO化** | 現時点で未確定だが暫定値で進められる | 性能目標、ユーザー数 |

下記1、2、6はブロッカーのため必ず質問する。3、4、5、7はTODO化して進めてよい。

1. 作成スコープ（全章フル作成 / 特定章のみ / 既存要件定義書の差分更新）
2. システムの種別（新規開発 / リプレイス / クラウド移行 / 機能追加 / バッチ主体）
3. 非機能要件の数値目安
   - 登録ユーザー数・同時接続数
   - 応答時間目標（オンライン／バッチそれぞれ）
   - 可用性・稼働率・許容ダウンタイム
4. 既存・関連システムの連携範囲
5. ID命名規則の踏襲有無
6. セキュリティ・コンプライアンス制約（認証方式の指定・適用規制・監査ログ要件）←顧客合意が必要なため必ず質問
7. 出力形式（単一 Markdown / 章別分割 / Word・Excel・PDF 変換の要否）

**そのまま投げられる確認文面**

```
- 今回の作成スコープ（全体フル / 特定章のみ / 既存書類の差分更新）はどれですか？
- 新規開発・リプレイス・機能追加など、どのシナリオに該当しますか？
- 想定ユーザー数とピーク時の同時接続数はどれくらいですか？
- 応答時間の目標（例: 3秒以内）と可用性目標（例: 99.9%）はありますか？
- 連携する外部システムはありますか？ある場合、連携方式（API / ファイル / DB直接）は？
- 認証方式の制約はありますか？（自社IdP・SAML/OAuth強制・IP制限など）← 6番の質問①
- 個人情報保護法・GDPR・業界規制など、適用する法令・コンプライアンス要件はありますか？← 6番の質問②
- 監査ログの要件はありますか？（保存期間・対象操作・外部転送の要否など）← 6番の質問③
- 納品形式は Markdown のみで良いですか？Word や PDF が必要な場合は教えてください。
```

## 作成手順

1. **目的とスコープを固定する（最重要・最優先）**
   - **目的の明確化**: 「誰の」「どんな問題を」「なぜ今」解決するのかを 1〜3 文で書く。RFP に書いてあっても自分の言葉で再記述する（曖昧なら BLOCKER）。
   - **対象範囲の境界設定**: 業務単位／組織単位／システム単位のどれで切るかを明示。境界が曖昧なまま要件を集めると後で爆発する。
   - **対象外の明示**: 「やらないこと」を最低 3 件は書く。よくある対象外候補: 既存システムの改修、他部門業務、データ移行、外部連携の追加 等。判断保留は `【TODO(BLOCKER): スコープ確認】` で即アラート。
   - **前提条件**: 既に決まっている事実（採用クラウド、利用ブラウザ、既存システム の前提）を `CON-XXX` で列挙。
   - **制約条件**: 顧客／法令／契約／技術 由来の縛り（指定言語、納期、予算、規制）を `CON-XXX` で列挙。
   - **曖昧な要望の仕分け**: 集まった要望を以下の3つに分類して整理:
     - 「要件」（FR/NFR/etc に昇格できるもの）
     - 「確認事項」（情報不足で判断不能 → `【TODO】` または `TBD-XXX`）
     - 「対象外候補」（スコープ外と合意できそうなもの → 5.2 対象外）

2. **業務要件を整理する**
   - As-Is/課題/To-Beを分け、業務フローまたはユースケースで表現する。
   - 業務上の成果、判断基準、利用者の責務を明確にする。

3. **システム要件へ分解する**
   - 業務要件を機能要件、画面要件、帳票要件、データ要件、外部連携要件、バッチ要件に分ける。
   - 各要件にはID、優先度、根拠、受入条件、関連業務要件を付ける。

4. **非機能要件を定義する**
   - 「速い」「安全」などの形容詞だけで終わらせず、測定可能な条件に落とす。
   - 未確定の場合は暫定値と確認先を記載する。

5. **合意事項と未決事項を分離する**
   - 決定済み、仮決定、確認中、対象外を表で管理する。
   - 未決事項には担当、期限、影響範囲を付ける。

6. **基本設計への接続を作る**
   - 要件IDと後続成果物の対応を作れるよう、トレーサビリティ表を用意する。
   - 基本設計で扱うべき画面、API、DB、処理フロー候補を抽出する。

## シナリオ判定

**判定ツリー**（上から順に評価し、最初に Yes になったシナリオを採用する）

1. エンドユーザー向けの操作画面がなく（運用管理画面のみは可）、定期実行・システム間データ処理が中心か？ → **バッチ/データ処理**
2. 既存稼働中システムへの機能追加・改修で、システム全体は維持されるか？ → **機能追加/改修**
3. 既存システムを別実装で再構築する（機能・データを引き継ぐ）か？ → **リプレイス/再構築**
4. アプリケーションは現状維持で、インフラ／実行基盤のみ変更するか？ → **クラウド移行**
5. 上記いずれにも該当しない（ゼロから作る）→ **新規開発**

複数該当する場合（例: リプレイス＋新機能追加）は、主シナリオをベースにし、他シナリオの重点観点を補強する。

**シナリオ別の重点**

| シナリオ | 必須章 | 特に重点を置く観点 |
|---|---|---|
| 新規開発 | 1,2,4,5,6,7,8,9,11,13,14,15 | 目的・成功基準・MVP範囲・優先度・受入条件 |
| リプレイス/再構築 | 1〜15 全章 | 現行機能の踏襲/廃止/改善・移行・並行稼働・切替条件 |
| クラウド移行 | 1,2,3,5,8,9,11,12,13,14,15 | 非機能・外部接続・責任分界・移行・切戻し |
| 機能追加/改修 | 1,2,5,6,11,13,14,15 | 変更対象・既存影響・差分要件・リリース条件 |
| バッチ/データ処理 | 1,2,5,8,9,10,11,13,14,15 | 入出力・処理頻度・締め時間・リカバリ・データ品質 |

## 要件定義と基本設計の境界

迷ったら「**顧客と合意すべきか（要件定義）／設計者・開発者が決めてよいか（基本設計以降）**」で判断する。

| 領域 | 要件定義（本スキルの範囲） | 基本設計以降（範囲外） |
|---|---|---|
| 画面 | 必要な機能・表示する情報・ロール別アクセス方針 | 画面レイアウト・コンポーネント・遷移の詳細 |
| API / 連携 | 連携先・入出力概要・方式種別・頻度・責任分界 | エンドポイント設計・パラメータ詳細・OpenAPI |
| データ | 主要エンティティ・保持期間・移行方針・CRUD方針 | テーブル定義・インデックス・SQL |
| バリデーション | 「何を検査するか」（必須・桁数・形式種別） | 正規表現・実装方式 |
| **非機能** | **数値目標・達成条件・根拠（SLA等）・優先度** | **測定方法・合格判定・検証スクリプト要否** |
| エラー | ユーザー影響・業務上の対応方針 | エラーコード体系・例外クラス設計 |
| アーキテクチャ | 技術選定の制約（指定言語・指定インフラ等の顧客制約） | 採用ライブラリ・レイヤー責務・横断ルール（基本設計 2.4） |

> **非機能の重複に注意**: 要件側 11章は「**目標値・根拠**」（What、顧客と合意する）、基本設計 8章は「**測定方法・合格判定**」（How、エンジニアが追加する）。要件側で測定方法まで書き込まないこと（基本設計の領分を侵食する）。要件側 non-functional-requirements.md には「測定方法」列があるが、これは**基本設計への申し送り欄**であり、確定した測定スクリプトは基本設計側で作成する。

**受入条件（AC-）の運用ルール（重要）**

`AC-XXX` は **13章「受入観点・受入基準」を Single Source of Truth (SSoT)** とし、全要件横断のマスタとして管理する。各要件詳細表（6.2 機能要件、7.2 画面要件 等）は **AC本体を書かず、`関連受入条件ID` 列で AC-XXX を参照**する。

| NG（二重定義） | OK（参照に統一） |
|--------------|----------------|
| 6.2 に「受入条件」列で文章を書き、13.3 にも AC-001 として同じ内容を書く | 6.2 は「関連受入条件: AC-001, AC-002」、本体は 13.3 のみ |

> 受入条件の本文を 6章 や 7章 に直書きしない。13章に集約することで、`test-design` / `release-readiness` がレビュー対象を一覧化できる。

## レビューポイント

執筆完了時、レビュー観点を3階層に分けて提示する。

**1. 顧客レビュー（外部要件の合意）**
- 1章 はじめに、2章 プロジェクト概要（目的・成功基準・制約）
- 4章 To-Be業務要件（業務フロー・ユースケース・業務ルール）
- 5章 システム化範囲（対象・対象外・責任分界）
- 11章 非機能要件（性能・可用性・セキュリティの数値）
- 13章 テスト・受入要件（受入基準・検収条件）

**2. PL/PMレビュー（スコープ・整合性）**
- 全章 × スコープ定義との整合
- 優先度の根拠が説明できるか
- 未決事項（14章）に担当・期限が付いているか
- TODO が放置されていないか

**3. 開発チームレビュー（実装可能性・後続接続）**
- 6章 機能要件・7章 画面帳票要件・8章 データ要件・9章 外部連携要件・10章 バッチ要件
- 各要件が基本設計に引き継げる粒度か
- 11章 非機能要件の数値が実現可能な範囲か
- 15章 トレーサビリティで基本設計候補が見えているか

**機械的整合チェック（出力前に必ず自律実行）**

人間レビューの前に、以下のクロスチェックを機械的に実行し、不整合があれば修正してから出力する。

| チェック項目 | チェック方法 |
|------------|------------|
| 全 `BR-XXX` が少なくとも 1 つの `FR-XXX` / `NFR-XXX` と紐付いているか | 15.1 トレーサビリティ表で全 BR を grep |
| 全 `FR-XXX` が「画面候補」「API候補」「データ候補」「処理フロー候補」のいずれかにマップされているか | 15.2 を全 FR で確認 |
| 全 `NFR-XXX` が少なくとも 1 つの `AC-XXX` と紐付いているか | 11章 関連受入条件ID 列を確認 |
| 13.2 の `AC-XXX` の「対象要件ID」が実在する要件 ID か | AC 表の対象要件IDを抽出し、6/7/8/9/10/11章の要件 ID 群と突合 |
| 6.2 / 7.2 / 11章の `関連受入条件ID` が 13.2 で定義済みか | 各表の AC-XXX を抽出し、13.2 の AC マスタと突合 |
| 曖昧語（「高速」「大量」「適切」等）が本文に残っていないか | grep で検出 |

**実行手段の優先順位**:
1. **第一選択**: `waterfall-delivery-cycle/scripts/validate_traceability.py` が利用可能なら実行する。`docs/traceability.json` の ID 重複・リンク参照・AC→TC 到達性を機械的に検証。
2. **第二選択**: スクリプトが無ければ `Grep` で各 ID を突合する。
3. **フォールバック**: いずれも使えない環境では Read で全章を読み込み、メモリ上で ID を突合する。「ツールが無いから諦める」は禁止。

**TODO 集約レポート**

本文中の `【TODO(BLOCKER): ...】` と `【TODO: ...】` を全件抽出し、以下の属性を付けて一覧化する。

| 列 | 内容 |
|---|---|
| 種別 | BLOCKER / 通常 |
| TODO本文 | 該当箇所の文言 |
| 章・セクション | 章番号と見出し |
| 確認先 | 顧客／PM／開発／法務 など |
| ブロッカー度 | 要件FIX前必須 ／ 基本設計フェーズ可 ／ 運用フェーズ可 |
| 期限目安 | レビュー日からの逆算 |

> **BLOCKER 級の TODO は発見時点で即時アラートしているため、本レポートでは「未解決のまま残っているか」の最終確認に位置づける。** ここで初めて報告するのではない。

## 書き方の原則

- 顧客合意に必要な粒度を優先する。
- 実装方法ではなく、業務上・システム上の要求と制約を書く。
- 事実、仮説、提案、未決事項を混ぜない。
- 要件はテスト可能な文章にする。
- 既存資料の表現を尊重しつつ、曖昧さは補足欄で可視化する。
