# 公式・準公式Baseと実務への落とし込み

## 位置づけ

このスキルは、標準をそのまま転記するものではなく、要件定義作業で参照すべき観点を実務テンプレートに落とし込むためのもの。

優先順位:

1. 顧客指定テンプレート、社内標準、過去案件様式
2. 公的・準公的Base
3. 既存の基本設計スキルへ渡すための実務構成

## 公的・準公的Base

| Base | このスキルで使う観点 |
|---|---|
| ISO/IEC/IEEE 29148:2018 | 要件工学プロセス、良い要件の性質、要件情報項目、要件管理、妥当性確認・検証 |
| IPA 共通フレーム2013 | 日本SIでの共通語彙、利害関係者との合意、要件定義プロセス、システム/ソフトウェア開発ライフサイクル上の位置づけ |
| IPA 非機能要求グレード2018 | 非機能要求を網羅的に洗い出し、利用者と開発者の認識齟齬を減らすための分類・確認観点 |
| 共通フレーム2013に基づく調達管理ガイド | 調達仕様書・要件定義で必要になりやすい記載事項。機能、画面、帳票、情報・データ、外部IF、性能、信頼性、拡張性、テスト、移行など |

参照URL:

- ISO/IEC/IEEE 29148:2018: https://www.iso.org/standard/72089.html
- IPA 共通フレーム2013: https://www.ipa.go.jp/publish/secbooks20130304.html
- IPA 非機能要求グレード: https://www.ipa.go.jp/sec/softwareengineering/std/ent03-b.html
- IPA 共通フレーム2013に基づく調達管理ガイド: https://www.ipa.go.jp/archive/files/000029060.pdf

## 実務への落とし込み

### ISO/IEC/IEEE 29148:2018 由来

- 要件は、利害関係者要求、システム要求、ソフトウェア要求に分けて扱う。
- 要件は一意に識別し、属性、根拠、優先度、状態、検証方法を持たせる。
- 要件は検証可能で、曖昧さが少なく、追跡可能であることを重視する。
- 要件定義は一回で終わる作業ではなく、識別、分析、合意、管理を反復する。

### IPA 共通フレーム2013 由来

- 利害関係者の識別、要件の識別、要件の評価、要件の合意を明示する。
- 要件定義は発注者・受注者・業務部門が同じ言葉で合意するための作業として扱う。
- 機能要件と非機能要件だけでなく、運用、移行、保守、役割分担まで含めて確認する。

### IPA 非機能要求グレード2018 由来

- 非機能要件は、性能、可用性、拡張性、運用・保守性、移行性、セキュリティ、システム環境などを網羅的に確認する。
- 「高速」「安全」「止まらない」などの表現は、要求レベル、目標値、前提条件、測定方法に落とす。
- 全項目を詳細化するのではなく、重要項目から要求レベルを決める。

### 調達管理ガイド由来

- 機能要件だけでなく、画面要件、帳票要件、情報・データ要件、外部インタフェース要件を分ける。
- 規模・性能、信頼性、拡張性、システム中立性、運用、テスト、移行を要件として扱う。
- 外部IFは、接続先、データ、方向、手段、タイミング、開始/終了条件、接続確認条件を整理する。

## 基本設計スキルへの接続

要件定義では、基本設計の成果物を確定させすぎない。ただし、後続で設計漏れが起きないように、次の候補を残す。

| 要件定義の要素 | 基本設計で具体化する候補 |
|---|---|
| 画面要件 | 画面一覧、画面遷移、画面詳細 |
| 帳票要件 | 帳票一覧、出力項目、出力条件 |
| データ要件 | ER、テーブル、データ保持、移行 |
| 外部IF要件 | API、ファイル連携、外部システム連携 |
| バッチ要件 | 処理フロー、スケジュール、リカバリ |
| 非機能要件 | 性能設計、可用性設計、セキュリティ設計、運用設計 |

## 採用しないもの

- 特定規格の章番号や文言の完全再現。
- 顧客テンプレートがある場合の独自章立ての強制。
- 詳細設計レベルの実装方式、クラス、関数、物理DB設計。
