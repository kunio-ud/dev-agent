# 基本設計書作成スキル

## このスキルの目的

日本のソフトウェア開発標準に沿った**基本設計書（外部設計書）**を作成する。
静的な構造（画面・DB・インターフェース）だけでなく、**動的な振る舞い（処理フロー・シーケンス）**を明確に定義する。
また、**OpenAPI (Redoc)** や **Mermaid** を活用し、ドキュメントの保守性と視覚的な理解を両立させる。

### 用語定義

本SKILLでは「**基本設計書**」と「**外部設計書**」を同義として扱う。

| 用語 | 本SKILLでの位置づけ | 対応する観点 |
|------|------------------|--------------|
| 基本設計（外部設計） | 本SKILLが対象 | **What ＋ How を縛る制約**：外から見た振る舞い（画面・API・データ・非機能）に加え、後続の実装フェーズで揺れさせない**実装制約（採用ライブラリ、レイヤー責務、横断ルール）**を含む |
| 詳細設計（内部設計） | 本SKILLでは扱わない | **How**：クラス構造・関数仕様・アルゴリズム・変数命名など |

「基本設計／外部設計」の語は、SIer文化では同義、自社開発文化では区別されることもあるが、本SKILLでは混乱を避けるため**同義として併記**する。

> **重要**: 「詳細設計を扱わない」≠「実装に丸投げ」。本SKILLは**「Howは詳細設計に委ねるが、Howを縛るための制約は基本設計で必ず合意する」** という立場を取る。詳しくは Step 3 の「2.4 アーキテクチャ方針・実装制約」と [architecture-policy.md](./assets/templates/architecture-policy.md) を参照。

## 使用場面

以下のような場面で本SKILLを使用する。

- 要件定義書をインプットとして基本設計書（外部設計書）を新規作成する
- 既存システムをリプレイス／クラウド移行する際の設計書を作成する
- 既存システムのリバース設計書（現状の動作を文書化）を作成する
- 機能追加・改修の差分設計書を作成する
- 設計レビューに向けて、画面・DB・IF・処理フロー・非機能要件を体系的に整理する

**本SKILLが扱う粒度**: 基本設計（外部設計）= 「外から見た振る舞い（What）」が中心。実装アルゴリズム・変数名・クラス構造などの「How」は詳細設計フェーズで扱うため、本SKILLでは扱わない。

## 手順

### Step 1 — インプット収集とブロッカー早期検知

執筆を始める前に、以下のインプットを集める。

**TODO の 2 種類の使い分け（重要）**

| 記法 | 用途 | 即時アラートの要否 |
|------|------|---------------|
| `【TODO(BLOCKER): 〇〇を確認】` | これが未解決だと**設計FIX前に必須**。実装着手不可レベル（API IO・DB主要キー・認証方式・主要業務フロー等） | **ユーザーへ即時アラート**（Step 4 を待たない） |
| `【TODO: 〇〇を確認】` | 詳細設計／運用フェーズで決めても進められる項目 | Step 4 の TODO 集約レポートへ |

**ブロッカー項目を見つけたら、その章の執筆完了を待たず、即座にユーザーに対して質問・アラートを出す。** 設計書を書き終えてから「実は不明でした」を出すと、後続の実装フェーズが止まる。

**必須インプット**
- 要件定義書（業務要件 `BR-XXX`、機能要件 `FR-XXX`、非機能要件 `NFR-{分類}-XXX`、受入条件 `AC-XXX`、ユースケース、業務フロー）
- `docs/traceability.json`（要件と設計成果物の紐付けの正本）
- システムの目的・背景・主要ステークホルダー
- 機能一覧（`FR-XXX` 粒度）

**あれば望ましいインプット**
- 既存システムのドキュメント（リプレイス・改修時）
- アーキテクチャ方針・技術選定資料
- 過去のインシデント／運用実績（非機能要件の根拠）
- セキュリティ・コンプライアンス要件
- 既存ID命名規則（あれば踏襲、なければ本SKILLの規則を採用）

**着手前にユーザーに確認すべき項目**

不明な場合は推測せず質問する。回答が後でも進められる項目は TODO に逃がす。**特に「実装ブロッカー」になる項目（★印）は最初に確認する。**

1. 設計書のスコープ（フル設計 / 差分設計 / 特定章のみ）
2. 想定規模・性能要件 — 8章 非機能要件の TODO を減らすため、以下を最初に確認する
   - 登録ユーザー数・アクティブユーザー数・データ件数
   - ピーク時同時接続数（同時操作ユーザー／同時セッション）
   - 月間／日次トランザクション数（主要操作ごと）
   - 応答時間目標（オンライン処理／バッチ処理それぞれ）
   - 可用性目標（SLA／稼働率／許容ダウンタイム）
3. 既存・関連システムの有無と連携範囲
4. ID命名規則の踏襲有無
5. 出力形式（単一 Markdown / 章別分割 / Word・Excel・PDF 変換の要否）
6. セキュリティ・コンプライアンス制約 — 「あれば望ましいインプット」に資料がない場合は最低限以下を口頭確認する
   - 認証方式の指定（自社IdP／OAuth／SAML 等の縛り）
   - 該当する業界規制（個人情報保護法／GDPR／PCI DSS／医療系・金融系の規制 等）
   - 監査ログ要件（保管期間・改ざん防止）
7. ★**アーキテクチャ方針（実装ブロッカー）** — 後続の実装フェーズが止まるため、最初に確認する
   - 採用言語・Webフレームワーク・主要ライブラリ（DB アクセス、バリデーション、認証）
   - 既存コードベースの有無（あればレポジトリ位置と既存規約の参照先）
   - レイヤー構成方針（Controller / Service / Repository を分けるか、関数型/OOP 方針）
   - 詳細は [architecture-policy.md](./assets/templates/architecture-policy.md) のチェックリストを参照

### Step 2 — 章構成を決定する

**必ず先に [references/chapters.md](./references/chapters.md) を読む。** 標準11章のフル構成と、シナリオ別推奨章構成（新規Web／リプレイス／クラウド移行／差分／バッチ）が定義されているため、本SKILLの章選択はこのファイルを正とする。

**進め方**

1. Step 1 のインプットから下記の判定ツリーでシナリオを決める。
2. [references/chapters.md](./references/chapters.md) の「シナリオ別推奨章構成」から該当する章を抽出する。
3. 採用章・省略章・追加章をユーザーに提示し、合意を取ってから Step 3 へ進む。
4. シナリオが曖昧な場合（例：新規だが既存システム連携あり）は、最寄りのシナリオをベースに章を加減した提案を出す。

**シナリオ判定ツリー**

上から順に評価し、最初に Yes になったシナリオを**ベースシナリオ**として採用する。
複数該当する場合はベースに他シナリオの章を補強する。

1. **エンドユーザー向けの利用画面がなく**（運用管理画面のみは可）、定期実行・システム間連携が処理の中心か？ → **バッチ処理システム**
2. 既存稼働中システムへの機能追加・改修で、システム全体は維持されるか？ → **機能追加・改修（差分）**
3. 既存システムを別実装で再構築する（機能・データを引き継ぐ）か？ → **既存システム再構築（リプレイス）**
4. アプリケーションは現状維持で、インフラ／実行基盤のみ変更するか？ → **クラウド移行**
5. 上記いずれにも該当しない（ゼロから作る） → **新規Webアプリケーション**

> 判定1の補足: 業務ユーザーが日常的に画面操作するシステムはバッチに該当しない。逆に、24時間バッチ処理が主体で運用者向けのジョブ監視画面のみ持つシステムはバッチに該当する。

判定が割れる例（ハイブリッドケース）:
- 「リプレイス＋同時に新機能追加」→ ベースは**リプレイス**、新機能の差分章を併記
- 「クラウド移行＋アプリ刷新」→ アプリも書き直すなら判定3でリプレイスになる。**リプレイス**をベースにし、2章にクラウドサービス選定根拠を追加
- 「単純なクラウド移行」（コードはそのまま）→ 判定4の**クラウド移行**
- 「エンドユーザー画面ありのシステムへの大規模なバッチ機能追加」→ 判定2で**差分**判定。差分章でバッチ設計（6.4）を重点化

**シナリオ早見表**（詳細は [chapters.md](./references/chapters.md) 参照）

| シナリオ | 必須章 | 重点 |
|---|---|---|
| 新規Webアプリケーション | 1〜9（10省略可） | 4 画面・6 IF・7 処理フロー |
| 既存システム再構築（リプレイス） | 1〜10 | 10 移行設計を詳細化 |
| クラウド移行 | 1, 2, 3, 5, 6, 7, 8 | 2 にインフラ構成図／クラウドサービス選定根拠を追加 |
| 機能追加・改修（差分） | 変更対象章のみ | 変更前／変更後の対比表 |
| バッチ処理システム | 1, 2, 3, 5, 6.4, 7, 8, 9 | 7 アクティビティ図中心、画面は省略可 |

**ID命名規則の確認**

章構成と合わせて、以下のIDプレフィックスをユーザーに提示・合意する（既存規則があれば踏襲）。

| 種別 | 推奨プレフィックス | 例 |
|---|---|---|
| 業務要件 | `BR-` | `BR-001` |
| 機能要件 | `FR-` | `FR-001` |
| 画面 | `SCR-{モジュール}-` | `SCR-AUTH-001` |
| API | `API-` | `API-001` |
| テーブル | `TBL-` ＋ 物理名 | `TBL-001 / m_users` |
| 処理フロー | `FLOW-` | `FLOW-001` |
| エラーコード | `ERR-` | `ERR-AUTH-001` |

### Step 3 — 各章を執筆する

章ごとに [./assets/templates/](./assets/templates/) のテンプレートを使って記述する。

**章別テンプレート**

| 章 | テンプレート | 形式・ツール |
|----|------------|------------|
| 2.4 アーキテクチャ方針・実装制約 | [architecture-policy.md](./assets/templates/architecture-policy.md) | Markdown |
| 4 画面設計 | [screen-design.md](./assets/templates/screen-design.md) | Markdown + Mermaid |
| 5 テーブル定義 | [table-definition.md](./assets/templates/table-definition.md) | Markdown |
| 6 インターフェース設計（API設計方針） | [api-interface.md](./assets/templates/api-interface.md) | Markdown（方針のみ） |
| 6 インターフェース設計（API物理定義 = SSoT） | [openapi-template.yaml](./assets/templates/openapi-template.yaml) | **OpenAPI 3.1 (Redoc)** |
| 7 処理フロー | [process-flow.md](./assets/templates/process-flow.md) | **Mermaid** |
| 8 非機能要件 | [non-functional.md](./assets/templates/non-functional.md) | Markdown |
| 9 エラー設計 | [error-design.md](./assets/templates/error-design.md) | Markdown |

**シナリオ別の補助テンプレート**（章とは別軸で使用）

| 用途 | テンプレート | 適用シナリオ |
|------|------------|------------|
| 変更前／変更後の対比表、影響分析、ロールバック計画 | [diff-design.md](./assets/templates/diff-design.md) | 機能追加・改修（差分）／リプレイスの新機能差分 |

> **API設計の Single Source of Truth (SSoT) ルール**: API の物理的な定義（パス・IO・ステータスコード）は [openapi.yaml](./assets/templates/openapi-template.yaml) を**唯一の正**とする。Markdown 側 ([api-interface.md](./assets/templates/api-interface.md)) は OpenAPI に書けない／書きにくい「設計方針」「採用根拠」「横断ルール」のみを扱い、**API一覧表は手書きしない**（必要なら OpenAPI から CI で自動生成）。両者は API-ID（`API-XXX`）で相互参照する。

執筆時のルール（詳細な整合チェックは「品質チェックリスト」を正とする）：

- **API設計の SSoT ルール**: 物理定義は [openapi.yaml](./assets/templates/openapi-template.yaml) のみ。`api-interface.md` は方針・採用根拠・共通仕様の合意のみ記述し、API 一覧の重複記述は禁止。OpenAPI 側で `x-api-id: API-XXX` と `operationId`（キャメルケース）を必ず両方付与する。
- **アーキテクチャ方針**: 2.4 章で採用ライブラリ・レイヤー責務・横断ルールを必ず合意してから他章に進む。これが曖昧だと後続の `implementation-coding` フェーズが暴走する。
- **処理フロー**: 複雑な動きは Mermaid のシーケンス図／フローチャート／状態遷移図で視覚化する。**シーケンス図には正常系に加え、必ず最低 1 つ以上の準正常系（4xx/5xx・タイムアウト等）を含める**（[process-flow.md](./assets/templates/process-flow.md) 参照）。
- **仮置き箇所**: ブロッカー級は `【TODO(BLOCKER): 〇〇】` で明示し即時アラート、それ以外は `【TODO: 〇〇】` で Step 4 集約。

**詳細設計との境界（曖昧領域の判断基準）**

| 領域 | 基本設計（本SKILLの範囲） | 詳細設計（範囲外） |
|------|------------------------|-----------------|
| バリデーション | 「何を検査するか」（必須・桁数・形式種別） | 「どの正規表現で実装するか」 |
| エラーメッセージ | ユーザー向け文言、エラーIDと分類 | ログ出力フォーマット、例外クラス階層 |
| DB | 論理設計、物理名、CRUDマトリクス、主要インデックス方針 | パーティショニング詳細、統計情報、SQL チューニング |
| API | エンドポイント、IO、ステータスコード、認証方式 | コントローラ実装、DI構成、ミドルウェア順序 |
| 画面 | 項目定義、画面遷移、ロール別表示制御方針 | コンポーネント分割、状態管理ライブラリ選定 |

迷ったら「**顧客と合意すべきか（基本設計）／開発者だけで決めてよいか（詳細設計）**」で判断する。

### Step 4 — 機械的整合チェック ＋ レビューポイントを提示する

**Step 4a. 機械的整合チェック（出力前に必ず自律実行）**

人間レビューの前に、以下のクロスチェックを機械的に実行し、不整合があれば修正してから出力する。

**実行手段の優先順位**:
1. **第一選択**: `scripts/validate_traceability.py` / `validate_evidence.py`（`waterfall-delivery-cycle/scripts/`）が利用可能な環境ならこれを実行する。`docs/traceability.json` の ID 重複・リンク参照・AC→TC 到達性、`docs/evidence/{phase}.evidence.json` の schema・artifact sha256・blocker 件数を機械的に検証する。
2. **第二選択**: スクリプトが無い場合は `Grep` / `yq` / `jq` で突合（高速・正確）
3. **フォールバック**: いずれも使えない環境では、**全該当ファイル（openapi.yaml / process-flow.md / screen-design.md / error-design.md / architecture-policy.md）を Read で読み込み、メモリ上で ID を突合せよ**。「ツールが無いから諦める」は禁止。

| チェック項目 | チェック方法 |
|-------------|------------|
| OpenAPI の全 `operationId` が `process-flow.md` のシーケンス図に出現するか | `yq '.paths[][].operationId' openapi.yaml` の全件を `grep` で `process-flow.md` 内に確認 |
| OpenAPI の全 `x-api-id` が `screen-design.md` の「呼出API」列または `process-flow.md` のいずれかから参照されているか | 同上 |
| `screen-design.md` の全ボタン／アクションに対し、対応する API または画面遷移先が定義されているか | ボタン定義表をなめて、各行に `API-XXX` または `SCR-XXX` への参照があるか |
| エラーコード `ERR-XXX` が `error-design.md` で定義されているか（OpenAPI / process-flow / screen-design からの参照すべて） | `grep -oE 'ERR-[A-Z]+-[0-9]+'` で抽出し、`error-design.md` の定義表と差分を取る |
| `architecture-policy.md` の採用ライブラリと、本文中で言及されているライブラリ名に矛盾がないか | バリデーション・日付・ログ等のキーワードで本文を grep |
| 画面の「呼出API」列のID と OpenAPI の `x-api-id` が一致しているか | API-IDで突合 |

> **不整合があれば「ユーザーへ報告 → 修正 → 再チェック」を出力前に完結させる。** 「整合性は人間が見てください」で投げない。

**Step 4b. レビューポイント提示**

レビュー観点を **3階層** に分けて提示する。各章をレビュー対象別にタグ付けすることで、レビュー会の効率と論点の切り分けが明確になる。

**1. 顧客レビュー（外部仕様の合意）**
- 1章 はじめに、2章 システム概要、3章 機能一覧
- 4章 画面設計（特に画面遷移図と主要画面の項目定義）
- 8章 非機能要件（性能・可用性・セキュリティの数値）
- 9章 エラー設計（ユーザー向けメッセージ）

**2. PL/PMレビュー（要件整合性・スコープ）**
- 全章 × 要件定義書のトレーサビリティ照合
- 採用章がシナリオ判定と合致しているか
- TODO が放置されていないか

**3. 開発チームレビュー（実装可能性）**
- 5章 DB設計、6章 インターフェース設計、7章 処理フロー
- 状態遷移図とAPIシーケンスの整合性
- バリデーションルールが実装可能な粒度か
- API-ID と OpenAPI の operationId の対応

**Step 4c. TODO 集約レポート**

本文中の `【TODO(BLOCKER): ...】` と `【TODO: ...】` を全件抽出し、以下の属性を付けて一覧化する。

| 列 | 内容 |
|---|---|
| 種別 | BLOCKER / 通常 |
| TODO本文 | 該当箇所の文言 |
| 章・セクション | 章番号と見出し |
| 確認先 | 顧客／PM／開発／インフラ／法務 |
| ブロッカー度 | 設計FIX前必須 ／ 詳細設計フェーズ可 ／ 運用フェーズ可 |
| 期限目安 | 設計レビュー日からの逆算 |

> **BLOCKER 級の TODO は Step 1 / Step 3 の発見時点で即時アラートしているため、Step 4c では「未解決のまま残っているか」の最終確認に位置づける。** ここで初めて報告するのではない。

### Step 5 — 出力

**出力先**

- 標準: `docs/design/` 配下（プロジェクトの慣例があればそれを優先）

**命名規則**

**最終成果物セット**

1. 章別 Markdown ファイル群（または単一 `basic-design.md`）

**レンダリング前提**

- Markdown / Mermaid: GitHub・VSCode Preview・GitLab で表示確認
- OpenAPI: Redoc または Swagger UI でレンダリング

**Word / Excel / PDF 納品が必要な場合の運用**

SIerの納品物としてWord/PDFが要求されるケースは多い。以下の方針を Step 1 で確認し、最初から運用に組み込む：

| 納品形式 | 推奨運用 |
|---------|---------|
| Word | Pandoc で `.md` → `.docx` 変換。Mermaid は事前に PNG エクスポートして `![](path/to/img.png)` に置換するスクリプトを用意 |
| PDF | Pandoc + LaTeX、または VSCode 拡張 (Markdown PDF) で出力。OpenAPI は Redoc の static HTML を PDF 印刷 |
| Excel | テーブル定義・画面一覧などの表形式は `.md` 表 → CSV → Excel 取込が現実的。設計書全体の Excel 化は非推奨 |

**Mermaid 図の二重管理回避**: Word/PDF 納品が確定している場合は、最初から `docs/design/assets/diagrams/{図ID}.png` に画像を配置し、Markdown では `![](assets/diagrams/xxx.png)` で参照する運用に統一する（Mermaid ソースは別途 `.mmd` で保管）。

## 記述スタイルガイド

- **対象読者**: 開発エンジニア・PLを想定し、実装判断できる粒度で書く
- **文体**: 体言止め・箇条書きを優先。長文の説明は避ける

- **数値**: 曖昧表現（「高速に」「大量の」）を使わず、具体的な数値で記述する
- **図表番号**: 「図 1-1」「表 2-3」形式で採番する
