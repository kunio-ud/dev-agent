# アーキテクチャ方針・実装制約テンプレート

> **位置づけ**: 本書（基本設計 2.4）は **顧客と合意可能な「方針」レベル** に留める。実装の具体形（命名、ディレクトリ構成、エラーの具体的な型、ログの正確なフォーマット、import順序等）は `project-coding-rules` スキルで生成する `docs/development/CODING_RULES.md` に委譲する。
>
> **役割分担（重要・厳守）**:
>
> | 文書 | 守備範囲 | 読み手 |
> |------|---------|-------|
> | **本書（2.4）= 案件単位の方針** | 採用ライブラリの「選定」、レイヤー「責務」、横断ルールの「方針」 | 顧客、PL、`project-coding-rules`、`implementation-coding` |
> | **CODING_RULES.md = リポジトリ単位の実装ルール** | 命名規則、ディレクトリ構成、エラーの具体的な型、ログフォーマット、import順序、Lint設定 | `implementation-coding` |
>
> **本書に書かないこと**: ロガー出力フォーマット、エラークラスの実装、ファイル命名規則、import順序、テストフレームワークの assertion スタイル等 — すべて CODING_RULES.md 側で具体化する。

## 2. レイヤー構成と責務（方針）

```
[Controller / Handler]   ← HTTP・画面入出力、認証認可、入力バリデーション
        ↓
[Service]                ← 業務ロジック、トランザクション境界
        ↓
[Repository]             ← DBアクセス、外部API呼び出しの抽象化
        ↓
[Infrastructure]         ← DB、外部システム
```

| レイヤー | 責務 | 禁止事項 |
|---------|------|---------|
| Controller / Handler | HTTPレイヤーの入出力、リクエストバリデーション、認証・認可、レスポンス整形 | 業務判断、DB直接アクセス |
| Service | 業務ロジック、Repositoryのオーケストレーション、トランザクション境界 | HTTPに依存する処理、DB SQL直書き |
| Repository | DBアクセス、外部API呼び出しの抽象化 | 業務判断（業務ルール条件分岐） |

**業務ロジックの置き場所**: Service 層に集約する。Controller・Repository に業務判断を入れない。

> 具体的なディレクトリ配置・ファイル命名・関数名規則は CODING_RULES.md に委譲。

## 3. プログラミングパラダイム方針

| 項目 | 方針 | 例外 |
|------|------|------|
| 関数型 / OOP | 関数型を基本（純粋関数、不変データ） | 外部フレームワークが class を要求する場合 |
| TypeScript | `class` と `this` を使わない | NestJS / TypeORM 等の強制時のみ |
| 例外 vs Result | 「想定済みエラー」は Result/Either 型などで返し、「想定外エラー」のみ throw | 既存コードベースが例外中心の場合は踏襲 |
| 共有 mutable state | 禁止 | グローバルキャッシュ等は理由明記の上で許可 |

> Lint ルール、tsconfig、具体的な書き方の例は CODING_RULES.md に委譲。

## 4. 横断的関心事の選定（ライブラリ名のみ）

実装の揺れを防ぐため、以下は**指定ライブラリで統一**する。**具体的な使い方・wrapper の有無・設定値は CODING_RULES.md で定義**する。

| 関心事 | 採用ライブラリ | 用途 |
|--------|--------------|------|
| バリデーション | （例: zod / valibot） | 全 API 入力 |
| 日付・時刻 | （例: date-fns / Temporal API） | UTC保管・JST表示 |
| ID生成 | （例: ULID / UUIDv7） | DB主キー |
| HTTPクライアント | （例: fetch / ofetch） | 外部API呼び出し |
| ロガー | （例: pino） | 構造化ログ |
| 環境変数 | （例: zod でスキーマ検証） | 起動時 fail-fast |

## 5. データ整合性・トランザクション方針

| 項目 | 方針 |
|------|------|
| トランザクション境界 | Service 層で開始・コミット |
| 排他制御 | （例: 楽観ロック / version カラム） |
| 一意制約違反 | DB 制約で検出し、Service で業務エラーに変換 |
| 冪等性（更新系API） | Idempotency-Key ヘッダ対応の要否を案件単位で決める |
| 外部API リトライ | 指数バックオフで最大 3 回 |

## 6. エラー分類方針

| 分類 | HTTPステータス相当 | 扱い |
|------|----------------|------|
| 業務エラー | 4xx | ユーザー向けメッセージ、`ERR-XXX` を付与（→ [error-design.md](./error-design.md)） |
| システムエラー | 5xx | リトライ可否を判定、運用通知 |
| 想定外（バグ） | 5xx | スタックトレース取得、即アラート |

> エラークラスの実装、ログ出力フォーマット、構造化ログの必須フィールド、PII マスキング処理の具体形は CODING_RULES.md に委譲。

## 7. テスト方針（粒度・カバレッジのみ）

| 区分 | 方針 |
|------|------|
| 単体テスト対象 | Service 層、純粋関数、複雑なバリデーション |
| Repository テスト | 実DB or testcontainers のいずれかを案件単位で決める |
| カバレッジ目標 | 行カバレッジ 80% 以上、Service 層 90% 以上 |

> 採用テストフレームワーク、assertion スタイル、テストファイル配置、命名規則は CODING_RULES.md に委譲。詳細なテスト観点は `unit-test-design` / `test-design` で作成。

---

## 8. セキュリティ方針

| 項目 | 方針 |
|------|------|
| 認証方式 | Bearer Token (JWT) / OAuth / SAML 等のいずれを採用するか |
| 認可方針 | Service 層でリソース所有権を必ず検証 |
| 通信暗号化 | TLS バージョン、内部通信の扱い |
| 機密データ保管 | パスワードハッシュ方式、PIIの暗号化、鍵管理 |
| シークレット管理 | リポジトリにコミット禁止、Secrets Manager 等の利用 |

> 具体的な認証ミドルウェア構成、CSRF対策の実装、暗号化ライブラリの呼び出し方は CODING_RULES.md に委譲。

## 9. 後続フェーズへの引き継ぎ事項

本章で**意図的に下流フェーズに委ねた事項**を明示する。

| 項目 | 委譲先 | 理由 |
|------|--------|------|
| ファイル命名・ディレクトリ構成 | `project-coding-rules` → `CODING_RULES.md` | リポジトリ単位で具体化 |
| エラークラス実装、ログフォーマット | `project-coding-rules` | 言語・FW依存 |
| Lint・Formatter 設定 | `project-coding-rules` | リポジトリ単位 |
| テストフレームワーク選定・assertion スタイル | `project-coding-rules` | リポジトリ単位 |
| 個別 SQL チューニング・インデックス追加 | 詳細設計／実データボリューム確認後 | データ量依存 |

**`project-coding-rules` への引き継ぎサマリ**: 本章をインプットとして、CODING_RULES.md は本章の方針を「具体的なリポジトリ実装ルール」に展開する。本章とのズレが発生した場合は、本章を優先して CODING_RULES.md を修正する。
