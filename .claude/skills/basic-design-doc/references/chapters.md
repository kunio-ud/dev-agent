## シナリオ別推奨章構成

> シナリオ名は SKILL.md の判定ツリーと一致させる。SKILL.md 側を変更した場合は本ファイルも同期させること。

> **2.4 アーキテクチャ方針・実装制約は全シナリオで必須**。後続の `implementation-coding` フェーズが「ライブラリ・レイヤー責務・横断ルールが未定」のまま走らないようにするための章。詳細は [../assets/templates/architecture-policy.md](../assets/templates/architecture-policy.md) を参照。

### 新規Webアプリケーション

必須: 1, 2（2.4 を含む）, 3, 4, 5, 6, 7, 8, 9
省略可: 6.3外部連携（連携なしの場合）, 10（新規のため）

### 既存システム再構築（リプレイス）

必須: 1, 2（2.4 を含む / 新スタックを明示）, 3, 4, 5, 6, 7, 8, 9, 10
重点: 10（移行設計）を詳細化

### クラウド移行

必須: 1, 2（インフラ構成図 ＋ 2.4 を追加）, 3, 5, 6, 7, 8
追加: クラウドサービス選定根拠セクション
参照: AWS／Azure／GCP など採用クラウドの設計ドキュメント

### 機能追加・改修（差分）

必須: 1（改訂内容のみ）, 変更対象章のみ
形式: 変更箇所を「変更前/変更後」対比表で示す（[diff-design.md](../assets/templates/diff-design.md) を使用）
2.4 の扱い: 既存方針を踏襲するなら省略可。新ライブラリ採用や既存方針からの逸脱がある場合のみ差分を記載。

### バッチ処理システム

必須: 1, 2（2.4 を含む / 冪等性・リトライ方針を必ず明記）, 3, 5, 6.4, 7（アクティビティ中心）, 8, 9
画面設計: 管理画面のみ（または省略）

## ドキュメント品質基準

### 粒度の目安

| フェーズ | 粒度 | 目的 |
|---------|------|------|
| 基本設計（外部設計） | What / 外から見た動作 | 顧客レビュー、詳細設計への橋渡し |
| 詳細設計（内部設計） | How / 内部実装 | 開発者が実装できるレベル |

基本設計書は「What」に留める。実装アルゴリズムや変数名は詳細設計書で扱う。

### トレーサビリティ

要件定義書の各要件IDと基本設計書の章・機能を対応付けること。

```
例: [REQ-001] ユーザーがログインできること
  → 画面設計: SCR-001 ログイン画面
  → API設計:  API-001 認証API
  → DB設計:   m_users テーブル
```

### レビューフェーズ

1. **作成者セルフレビュー** — 品質チェックリストを使用（SKILL.md参照）
2. **PL/PMレビュー** — 要件との整合性・スコープ
3. **顧客レビュー** — 外部仕様の合意
4. **開発チームレビュー** — 実装可能性の確認
